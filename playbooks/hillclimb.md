# Playbook: 单一量化指标科学爬山循环 (`hillclimb`)

> **设计溯源**：融合自 Lauren Tan (`pstack`) 的 `hillclimb` Playbook、`benchmark-checklist` 与 `explain-the-number` 原则。

---

## 1. 适用场景与触发条件 (When to Use)

当需求的目标**不是新增业务功能**，而是**针对某个可量化的单一工程指标进行持续逼近优化**时触发本剧本。典型场景包括：
* **性能与资源优化**：降低接口 P99 延迟、缩短构建/打包耗时、降低内存峰值、消除高频重渲染、提升吞吐量（QPS/TPS）。
* **体积与质量压缩**：缩减 Bundle 产物体积、提升特定算法/评估集（Eval）的准确率得分。

---

## 2. 角色分工链路 (Role Handoff Chain)

```
[planner] 识别量化优化目标 ➔ 标记 [HILLCLIMB] 并在 spec.md 定义基准测量命令与目标值
        │
        ▼
[dispatcher] 派发给 [coding] (若已有回归测试套件可跳过新增 TDD，直接锁死现有测试不破)
        │
        ▼
[coding] 执行「测基线 ➔ 单变量假说 ➔ 修改 ➔ 复测 ➔ 赢则 Commit / 输则立即 Checkout 回滚」循环
        │ (落盘每轮实验日志至 result.md)
        ▼
[reviewer-perf] 依据 Benchmark Checklist 核查测量有效性（排除假阳性与缓存作弊）
```

---

## 3. 分角色执行规程 (Step-by-Step by Role)

### 阶段一：`planner` 立项与标尺定义
在 `changes/<feat>/spec.md` 中必须明确标注 `[HILLCLIMB]`，并给出以下 4 个要素：
1. **唯一优化指标（Target Metric）**：例如 `冷启动构建耗时 (ms)` 或 `10万行解析内存峰值 (MB)`。
2. **确定性测量命令（Measurement Command）**：一条可重复运行、输出具体数值的命令。
3. **目标阈值与停止条件（Stop Criteria）**：例如“降至 500ms 以下，或连续 3 轮不同方向的假说均无法带来 ≥ 3% 的提升即停止”。
4. **正确性不变量（Correctness Guard）**：每次测量前必须保持全绿的现有测试命令。

### 阶段二：`coding` 科学爬山循环（核心执行者）
`coding` 严禁一次性把四五种优化手段混在一起改（那会导致无法分辨哪个改动有效、哪个改动甚至是负优化）。必须严格执行以下循环：

1. **Step 0 — 建立可信基线（Baseline）**：
   * 在未改任何代码前，连续运行测量命令至少 **3 次**，记录中位数与波动范围（Variance），确认当前环境的背景噪音水平。
2. **Step 1 — 瓶颈剖析与单变量假说（Hypothesis）**：
   * 基于 Profiler / Trace / 火焰图数据（而非盲目直觉），提出**一个且仅一个**具体假说：*“当前瓶颈在于 X；如果将 X 改为 Y，预期指标将改善，因为 Z。”*
3. **Step 2 — 最小化实验修改（Experiment）**：
   * 仅针对该假说编写代码修改，并确保正确性测试全绿。
4. **Step 3 — 复测裁决（Commit Winner / Revert Loser）**：
   * 在完全相同的条件下重新运行测量命令（至少 3 次取中位数）：
     * ✅ **显著改善（超出噪音波动范围且测试全绿）**：保留该改动，创建一个独立的原子 Commit（如 `perf(parser): 复用缓冲区降低分配开销 (-18% 耗时)`），将该成绩作为下一轮的新基线。
     * ❌ **退步、持平或在噪音范围内波动**：**严禁因“代码看起来更聪明”而保留无效优化！** 立即执行 `git checkout -- .` 彻底回滚该次尝试，在实验表中记录失败原因，转向下一个假说。
5. **Step 4 — 实验轨迹落盘**：
   * 在 `changes/<feat>/result.md` 中必须附上完整的爬山实验轨迹表（包含被回滚的失败尝试，为后续角色提供宝贵经验）：

   | 轮次 | 瓶颈假说 | 修改摘要 | 修改前指标 | 修改后指标 | 变化幅度 | 裁决结果 |
   | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
   | Baseline | — | 初始基线 (3次中位数) | 1,240 ms | — | — | 基线确立 |
   | #1 | 正则重复编译开销 | 预编译静态正则 | 1,240 ms | 1,235 ms | -0.4% (噪音内) | ❌ 已回滚 (`git checkout`) |
   | #2 | JSON 序列化深拷贝 | 改为流式零拷贝写入 | 1,240 ms | 780 ms | **-37.1%** | ✅ 采纳 (`commit a1b2c3d`) |

### 阶段三：`reviewer-perf` 真实性审计（Explain the Number）
`reviewer-perf` 收到爬山结果后，必须用以下清单审视数字的真实性，防止“跑分作弊”：
1. **解释数字背后的物理/逻辑上限（Explain the Number）**：为什么能快这么多？省掉的开销是否与 Profiler 中该函数的占比吻合？如果一个原本只占 5% CPU 的函数改完后总耗时降了 50%，说明**测错了东西或破坏了业务逻辑（比如把正常计算短路跳过了）**！
2. **排除基准测试陷阱**：是否因为缓存未清理、吞掉了异常报错、缩减了测试数据集，或者只改善了微基准（Micro-benchmark）却恶化了端到端（End-to-End）体验？
