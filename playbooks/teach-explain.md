# Playbook: 渐进式架构图解教学与人话降维 (`teach-explain`)

> **设计溯源**：融合自 Lauren Tan (`pstack`) 的 `teach`（`/how` + `/why` 图解编织）、`bro`（人话复述）与 Matt Pocock 的 `wait-what`（基于统一词汇表的上下文重述）。

---

## 1. 适用场景与触发条件 (When to Use)

当人类与 Agent 之间出现认知断层，或人类希望深入理解某个复杂设计/子系统时触发本剧本：
1. **即时困惑信号（`wait-what` 场景）**：人类发出“等等，这啥意思？”、“没看懂”、“太绕了，说人话”等信号，说明刚才的回复跳步太多或堆砌了过多实现黑话。
2. **深度架构/子系统教学请求（`teach` 场景）**：人类不仅想要一个结论摘要，而是明确表示“帮我彻底讲懂 X 模块是怎么工作的，以及当初为什么要这么设计”。

---

## 2. 角色分工链路 (Role Handoff Chain)

> ⚠️ **严格区分「当前方案解释」与「存量代码深潜」，保护 Window 1 上下文！**

```
[Human] 发出困惑信号或要求深入讲解某模块
        │
        ├── 情况 A：针对当前正在讨论的方案/架构概念（无需翻阅大量源码）
        │       ▼
        │   [planner] 直接读取 GLOSSARY.md，按「人话降维 + 递进式图解」就地解答
        │
        └── 情况 B：针对代码库中复杂的存量子系统（需深潜源码调用链与 Git 历史）
                ▼
            [planner] 通过 [dispatcher] 派发只读考古任务给 [explorer]
                │
                ▼
            [explorer] 执行 /how (调用链追踪) + /why (git log -S 历史溯源)
                │ (产出图文并茂的 docs/explanations/<topic>.md)
                ▼
            [planner] 基于 explorer 产出的文档，向人类进行渐进式图解导读
```

---

## 3. 分阶段执行规程 (Step-by-Step Guide)

### 规程一：即时人话降维（`wait-what` 模式 —— `planner` 就地执行）
当人类的反馈表明上一条消息没说明白时，严格执行以下 3 步重置沟通：
1. **找出缺失的上下文阶梯（Find the Missing Rung）**：刚才那段话之所以让人费解，通常是因为直接抛出了底层代码细节（如函数名、文件名、接口字段），而跳过了“它解决现实世界什么问题”。
2. **锚定 `GLOSSARY.md` 统一词汇**：用项目 `GLOSSARY.md` 中已达成共识的业务概念（或生活化类比）替代零散的技术黑话。
3. **先给全貌对比，再给单点决策**：用 3 句话讲清楚“之前是怎么样的 ➔ 哪里会出问题 ➔ 现在改成什么样”，绝不堆砌代码片段。

### 规程二：存量子系统深度教学（`teach` = `/how` + `/why` —— `explorer` 考古 + `planner` 导读）
当人类想真正吃透一个复杂子系统时，**严禁给出一堆干巴巴的文件名列表（如“`a.ts` 调了 `b.ts`，`b.ts` 又调了 `c.ts`”）**！必须将 **How（现在怎么转的）** 与 **Why（当年为什么长成这样）** 编织成递进式图解：

1. **Step 1 — `explorer` 双轨取证（若涉及存量代码）**：
   * **机制追踪（`/how`）**：追踪一条代表性请求/数据从入口边界到最终落盘的完整端到端轨迹，记录真实的数据结构形态变化（Data Shape Transformation）。
   * **历史考古（`/why`）**：使用 `git log -S "<关键符号>" -p`、`git blame` 及 `docs/adr/`，查明那些看起来“反直觉”或“复杂”的设计当年是为了修补什么边缘 Bug 或迁就什么性能/外部限制而引入的。
2. **Step 2 — 递进式图解构建（Build Up Diagram by Diagram）**：
   不要试图画一张包含 30 个节点的巨型蜘蛛网图！必须像剥洋葱一样，分成 **3 张由浅入深的 Mermaid 图** 逐层展开：
   * **图 1：黑盒心智模型（The Mental Model）** —— 站在外部调用者视角，输入是什么、输出是什么、核心不变量是什么（不超过 4 个节点）。
   * **图 2：核心数据流与状态流转（The Happy Path）** —— 打开盒子，展示核心组件在正常路径下如何传递和转换数据。
   * **图 3：历史棘手边界与防御机制（The Tricky Edge Case / Why It's Built This Way）** —— 专门标出那个最容易让人困惑的设计点，解释如果不这么做，在哪一步会发生什么灾难（并附上历史 Commit 或代码行号佐证）。
